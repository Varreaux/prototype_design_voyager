    NYU · AI for Games

    Design Voyager

    Autonomous Game Design via LLM-Powered Mechanic Discovery and Composition

    Benjamin Tian · Cody Jiang · Morgan Waddington · Ruimeng Yang · Ziyi Zhu
    Motivation

    Why is building good games hard?

    📚

    Knowledge Retention

    Designers "reinvent the wheel" every project. Past work rarely flows into the next one.

    +
    💡

    Creative Limitations

    Humans hit creative fatigue. When inspiration runs dry, the design process stalls.

    In the age of AI and significant automation,

    can we simplify the process of building games?

    Inspirations

    Building on prior work that inspired us

    Two key ideas shaped the foundation of our project.

    Voyager (2023)

    An open-ended, lifelong-learning agent in Minecraft.

    • Persistent memory of skills and artifacts.
    • Retrieves useful experiences as context for future decisions.
    • Enables continual improvement through accumulation.
    💡
    The Missing Piece

    No system combines automated mechanic generation with a persistent, growing library that stores and reuses successful mechanics.

    Boardwalk (2025)

    A framework for generating and evaluating board games with LLMs.

    • LLM generates game mechanics as executable code.
    • Automated playtesting with MCTS bots and multiple metrics.
    • Provides a strong evaluation pipeline for game mechanics.

    This insight led to our approach: Design Voyager, a lifelong-learning agent for game-mechanic discovery and composition.

    What we built

    Meet Design Voyager

    A lifelong-learning system that invents, codes, and validates game mechanics one at a time, and remembers every one it ships.

    Stateless generation
    ×

    Every prompt starts from scratch. No memory, no reuse.

    Lifelong library

    Each accepted mechanic seeds the next proposal. The library grows.

    How it works

    One full iteration of the loop

    1. 1Retrievesimilar mechanics from the library
    2. 2Proposea new mechanic via the LLM
    3. 3Compilecheck the generated code
    4. 4Playtestsimulate games and score them
    5. 5Verifydoes it change the game vs. baseline?

    Pass all gates: mechanic enters the library. Fail: one self-repair attempt, then discard.

    Method · Proposal Module

    Four context blocks, one new mechanic

    Every proposal is a single LLM call. We pack the prompt with four pieces of context so the model knows what to build on and what to avoid.

    • Game skeleton: the base rules of the card game.
    • Retrieved mechanics: the top-k most similar mechanics already in the library.
    • Library roster: the names of every mechanic we've accepted so far.
    • Ban list: names of mechanics that have already failed and shouldn't be re-proposed.

    Output is checked by a two-stage compile gate before anything else runs. Powered by Gemini 2.5 Flash.

    Method · Playtest Module

    Simulated play with two AI agents

    • Search engines: MCTS and minimax with tactical preambles, 100-turn cap.
    • Two-phase test: playability + balance (equal agents), then strategic depth (strong vs. weak).

    First simulates the base skeleton, then re-runs with the proposed mechanic spliced in.

    Method · Verification

    Delta-gated against a no-mechanic baseline

    • Simple gates: runtime stability and minimum thresholds on key metrics.
    • Delta gate: weighted relative score vs. baseline, with stage-aware thresholds.
    • Outcomes: Accept, Discard, or Revise, with a natural-language critique.
    Method · Self-Repair

    One repair attempt, then it's banned

    • Repair: failed mechanics get one corrective pass, guided by the critique.
    • Discard: a second failure ships the mechanic to the ban list.

    Keeps the loop honest without spending unbounded compute on a broken proposal.

    Method · Library

    A growing library of accepted mechanics

    • Storage: description, code, playtest scores, and vector embeddings per entry.
    • Retrieval: 0.7 semantic similarity + 0.3 performance score, with a per-run usage cap.
    • Diversity: full roster shown to the proposer, cosine-similarity reject at 0.92.
    Method · Curriculum

    Easy mechanics first, complex ones later

    • Progressive stages: three complexity tiers, advance after three consecutive accepts.
    • Stage-aware validation: complexity scope tightens; delta threshold loosens to match noisier complex mechanics.

    Avoids systemic collapse from overreaching early proposals.

    Method · Pair Lab

    From mechanics to combinations

    Game design is about interaction. So we measure pairs of mechanics, not just singles.

    • 190 pair combos, each with 30 simulated games.
    • 8 metrics per pair: balance, decisiveness, both-meaningful, length sanity, volatility, length CV, joint fire rate, non-greedy rate.
    Method · Fitness

    Which metrics actually predict fun?

    A human ranker sorted every pair into one of 5 buckets. We trained a simple linear regression mapping the 8 metrics to those buckets.

    The point is the learned weights, not the predictive ceiling: simple model, interpretable answer.

    Results · Surprising finding

    Our "fun" metrics got negative weights

    Three of the metrics we added specifically to capture interaction-driven fun (volatility, joint fire rate, decisiveness) ended up negative or near-zero.

    The fitness model also never predicts weak or not_fun. Either the 8 metrics don't span the negative end of fun-space, or a single rater's labels are too noisy to fit it. We can't tell yet which.

    Discussion

    Three limitations to address

    Limit 1
    One human ranker
    No inter-rater agreement; we can't put a ceiling on the model's achievable accuracy.
    Limit 2
    Post-placement only
    The engine can't run "block X / prevent Y" mechanics the LLM regularly proposes; they silently fail.
    Limit 3
    Depth-8 horizon
    Mechanics that pay out more than 8 turns ahead are invisible to the accept gate.
